# 网关 API网关 用户指南

## 产品简介

### 什么是API网关

API网关是围绕企业服务集成、接口托管和能力开放打造的稳定、可靠、可拓展的平台。通过平台快速实现新旧业务系统集成，以标准API的形式将系统服务开放出来，供各方使用；帮助企业轻松管理不同规模的 API，提升研发协作效率；通过微服务网关简单安全的实现成熟业务的能力开放与共享。 API网关提供了如下功能： 服务集成：支持对接注册中心实现服务发现和填写固定地址两种方式接入服务。 接口管理：提供了对服务接口生命周期的管理能力，包括创建、编辑、维护、调试、下线等。 网关路由：通过配置网关路由允许将服务公开给使用网关的客户端应用。 插件管理：提供多种系统插件，可实现重定向、设置请求头、重试、参数路由等功能。 流量控制：提供流量控制功能。限制流入的请求数，让服务免受冲击。 网关日志：提供请求日志查询功能。每条记录会显示调用时间、请求方法、请求URI、请求来源IP、返回码、耗时、请求响应数据等信息。 认证授权：提供客户端身份认证与接口授权功能。客户端身份认证支持Basic、JWT等方式。

#### 设置安全组规则

API网关能够访问后端服务有一个大前提，即位于同一个VPC内，但这并不意味着API网关就能直接访问后端服务，API网关和后端服务一般处于不同安全组内，您可以通过设置安全组规则为API网关授予访问后端服务的权限。

**背景信息**

安全组是一种虚拟防火墙，用于控制安全组内ECS实例和ENI网卡的入流量和出流量，从而提高ECS实例的安全性。安全组具备状态检测和数据包过滤能力，您可以基于安全组的特性和安全组规则的配置在云端划分安全域，详情请参见**《云服务器** **ECS** **用户指南》** > **安全组概述**章节。 API网关支持两种部署架构，EDAS部署架构和自定义部署架构。 在EDAS部署架构中，API网关实例必须与容器服务Kubernetes版ACK集群关联。ACK集群节点池的 VPC、VSwitch及安全组信息即为网关实例的相关信息。 在自定义部署架构中，API网关实例将被部署在租户侧的ACK或者EDAS中，需要用户自行保证实例所部署的节点与后端服务的安全组可访问。 因为API网关和后端服务所在的节点分别处于不同安全组内，需要您在后端服务的安全组内为API网关授予必要的端口范围访问权限。

**操作步骤**

1. 获取网关实例所在节点的网段。
i. 登录容器服务Kubernetes版控制台，在左侧导航栏选择**集群**。 ii. 在**集群列表**页面，单击目标集群名称，然后在左侧导航栏，选择**节点管理** > **节点池**，单击节点池名称。 iii. 在**节点池**页面，**节点配置**信息中获取**节点虚拟交换机**的ID。
2. 获取虚拟交换机所在的网段。
i. 登录专有网络 VPC控制台，在左侧导航栏选择**交换机**。 ii. 在**交换机**页面，找到步骤1获取的交换机，单击交换机ID。 iii. 在**基本信息**页签，**IPv4****网段**对应的值即为虚拟交换机所在的网段。
3. 获取目标服务所在节点的安全组。
API网关关联的上游服务，主要包括容器部署和ECS部署。您可以通过以下方式获取安全组ID。

**容器部署**

i. 登录容器服务Kubernetes版控制台，在左侧导航栏选择**集群**。 ii. 在**集群列表**页面，单击目标集群名称，然后在左侧导航栏，选择**节点管理** > **节点池**，单击节点池名称。 iii. 在**节点池**页面，**节点池信息**中获取**安全组**的ID。

**ECS部署**

i. 登录云服务器ECS控制台。 ii. 在左侧导航栏，选择**实例与镜像** **> ECS****实例**，单击目标服务所部署的ECS实例ID。 iii. 在**实例详情**页面，单击**安全组**页签，获取安全组的ID。
4. 添加安全组授权规则。
i. 登录云服务器ECS控制台。 ii. 在左侧导航栏，选择**网络与安全** > **安全组**，单击步骤3中获取的目标服务所在节点的安全组ID。 iii. 单击**安全组规则**页签，在**入方向**中单击**添加安全组规则**，配置以下参数后，单击**确定**。

| 参数 | 说明 | 示例 |
|---|---|---|
| 端口范围 | 输入安全组授权的端口范围。 | 1/65535 |
| 优先级 | 输入安全组规则的优先级。 | 1 |
| 授权类型 | 选择IPv4地址段访问。 | IPv4地址段访问 |
| 授权对象 | 填写步骤1中获取的网关实例所在节点的网段。 | 172.16.0.2/24 |

**常见问题**

**安全组已经授权，为什么服务还是访问不通？**

您可以按照如下步骤自助排查：
1. 首先需要确认您的目标服务所部署的节点是否正确。
有可能存在服务部署在了A节点上，但是给B节点所在的安全组授权。
2. 您的目标节点是否设置了多个安全组。
如果是多个安全组，建议给每个安全组都授权。

**安全组已经授权，之前网关访问服务是通的，现在突然间不通了，是什么原因？**

您可以按照如下步骤自助排查：
1. 首先确认您的服务本身没有问题。
您可以对同一安全组内的其他节点使用 `curl` 命令检查服务的连通性。
2. 确认您发布的服务对外暴露的端口是否有变更。
例如以前端口为8080，在API网关只给8080端口授权了，之后又将端口变更为8081，这时需要重新调整云安全组授权规则端口。为了避免这种情况发生，建议您在配置安全组授权时扩大端口范围，可以将范围填写为：1/65535。

#### 路由管理

服务创建好后，可以为服务创建对应的路由，路由管理提供了配置路由信息的功能。路由是服务提供统一的对外入口，用于接收用户请求并转发请求到对应的后端服务。

**创建路由**

1. 登录API网关控制台。
2. 在左侧导航栏，选择**API****网关** > **实例列表**或**API****网关** > **共享实例列表**。

5. 在**路由管理**页面，单击**创建路由**。
6. 配置相关选项后，单击**确定**，完成路由的创建。

| 参数 | 说明 |
|---|---|
| 路由分组 | 路由分组中创建的分组。 |
| 路由名称 | 自定义名称，支持最大长度128个字符。 |

| 路由路径 | 前端API路径是作为客户端应用的调用接口访问路径， 可填写多个， 支持精确匹配、占位符匹配和正则匹配 。 |
|---|---|
| 路由截取级数 | 开启后，路由路径转发到后台时会按照所指定的路径级数进行截取再转发至后台。 |
| 路由优先级 | 在路由路径相同的情况下，优先路由到优先级高的路由。数字越低，优先级越高。 |
| 请求方法/请求Header/请求Cookie/请求Query | 支持针对请求方法、请求头，Cookie和Query请求路径的参数进行配置，只有符合匹配规则的路由才可进行流量转发。 |
| 路由指向 | 可选择单服务和多服务。 |
| 启用状态 | 可打开或关闭路由状态。 |
| 后端服务 | 路由绑定的后端服务。 说明若需使用多服务灰度发布功能，需要至少有2个后端服务。 |
| 分组已关联域名 | 路由分组绑定的域名。 |
| 域名 | 路由绑定的后端域名。 |

#### 插件管理

##### 插件市场

**插件简介**

**插件市场**展示了本产品当前网关实例下的所有插件，通过这些插件可以实现请求或响应的改写、过滤、参数
映射等一系列功能。 插件可以分为两类：内置插件和自定义插件。 内置插件是本产品为所有网关实例提供的插件，其作用与使用方式在插件详情里均有介绍。 自定义插件是用户自行编写的插件。如果内置插件无法满足需求，用户可以自己编写自定义插件（自定义插件的编写说明会在下面介绍）。

**查看插件详情**

1. 登录API网关控制台。
2. 在左侧导航栏，选择**API****网关** > **实例列表**或**API****网关** > **共享实例列表**。
3. 在**网关实例**页面，选择指定实例，单击实例ID或**操作**列的**详情**。
4. 在左侧导航栏，选择**服务开放** > **插件管理** > **插件市场**。
5. 单击目标插件名称后，可以查看**插件详情**信息。
**基础信息**：描述了插件的名称与类型（自定义插件还会在此展示该插件的下载地址）。
**插件描述**：描述了插件的作用与使用方式。
**配置字段**：描述在使用该插件时，应该填写哪些配置字段，以及这些字段是否必填。
**使用情况**：描述了该插件在全局以及路由中的使用情况。

**创建自定义插件**

本产品支持自定义插件，即用户可以自行编写代码，封装为自定义插件并添加至网关中。首先，用户需要按照自定义插件编写说明，编写代码并打包为Jar包，然后将该Jar包上传至网关实例能够访问到的存储系统中 （例如阿里云OSS），从而得到该Jar包的一个下载地址。示例参考自定义插件编写说明。
1. 登录API网关控制台。
2. 在左侧导航栏，选择**API****网关** > **实例列表**或**API****网关** > **共享实例列表**。
3. 在**网关实例**页面，选择指定实例，单击实例ID或**操作**列的**详情**。
4. 在左侧导航栏，选择**服务开放** > **插件管理** > **插件市场**。
5. 在**插件市场**页面，单击**创建插件**。
6. 填写参数配置信息后单击**确定**，完成插件的创建。

| 参数 | 说明 |
|---|---|
| 插件名称 | 插件的名称。 |
| 下载地址 | 需要填写网关实例能够访问到的地址，网关实例会通过该地址将插件下载至本地并加载到内存中。如果网关实例无法访问该地址，插件无法生效。 |
| 插件描述 | 插件的描述信息。 |
| 配置字段 | 需要与自定义插件代码中编写的插件配置字段一致，否则配置字段无法生效。 |

创建完毕后，插件会展现在插件市场中，之后可以在全局插件以及路由插件中进行配置。

**代码示例**

项目中必须包含自定义插件类，自定义插件类的要求如下： 类名称必须为xxxGatewayFilterFactory的格式，且xxx为自定义插件的名称。（例如，在模板项目中， 自定义插件的名称是RequestTime，因此类名为RequestTimeGatewayFilterFactory）。

**重要**

插件名称不能随便取，必须与控制台中创建插件时填写的名称一致，否则无法生效！ 类必须继承Spring Cloud Gateway的AbstractGatewayFilterFactory类。 类中必须实现插件类的配置类，建议以子类的方式实现。例如，在模板项目中，配置类为 RequestTimeGatewayFilterFactory$Config，且配置类中的字段类型必须为String、Integer、 Boolean其一。

**重要**

插件配置类中的字段，必须与控制台中填写的配置字段一一对应，否则配置无法生效！ 类中必须实现apply方法，并返回一个GatewayFilter，在GatewayFilter.filter方法中编写自定义插件的逻辑。 下面是模板项目中的自定义插件类示例，这个插件RequestTime的作用为：计算请求在后端的响应时间， 并将该时间添加进Response Header中（header的name由配置header进行指定）。

```java
package com.example.customplugindemo.filter; import org.springframework.cloud.gateway.filter.GatewayFilter; import org.springframework.cloud.gateway.filter.GatewayFilterChain; import org.springframework.cloud.gateway.filter.factory.AbstractGatewayFilterFactory; import org.springframework.web.server.ServerWebExchange; import reactor.core.publisher.Mono; import java.util.Collections; import java.util.List; public class RequestTimeGatewayFilterFactory extends AbstractGatewayFilterFactory<RequestTimeGatewayFilterFactory.Config> {
    private static final String HEADER_KEY = "header";
    private static final String REQUEST_TIME_BEGIN = "requestTimeBegin";
```

```java
    public RequestTimeGatewayFilterFactory() {
        super(Config.class);
    }
    @Override
    public List<String> shortcutFieldOrder() {
        return Collections.singletonList(HEADER_KEY);
    }
    @Override
    public GatewayFilter apply(Config config) {
        return new GatewayFilter() {
            @Override
            public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain
chain) {
                exchange.getAttributes().put(REQUEST_TIME_BEGIN,
System.currentTimeMillis());
                return chain.filter(exchange).then(
                        Mono.fromRunnable(() -> {
                            Long startTime = exchange.getAttribute(REQUEST_TIME_BEGIN);
                            if (startTime != null) {
                                long requestTime = System.currentTimeMillis() -
startTime; exchange.getResponse().getHeaders().add(config.getHeader(), requestTime + "ms");
                            }
                        })
                );
            }
        };
    }
    public static class Config {
        private String header;
        public String getHeader() {
            return header;
        }
        public void setHeader(String header) {
            this.header = header;
        }
    }
}
```

#### 签名管理

**接入API签名**

为路由开启API签名后，匹配该路由的请求均需要携带签名信息，这就需要请求端接入API签名，为请求扩充签名信息。

**接入逻辑**

需要在请求的Header中携带以下签名相关信息。

| 字段 | 名称 | 说明 | 示例 |
|---|---|---|---|
| x-csb-sig-timestamp | 时间戳 | 请求发起的时间，用于签名时效性检查，单位为毫秒。 | 1654566424356 |
| x-csb-sig-expire | 过期时间 | 在请求发起后多久时效， 用于签名时效性检查，单位为毫秒。 | 60000 |
| x-csb-sig-scheme | 签名方案 | 路由配置的签名方案ID。 | 85fef190-5cfe-42c6- a50c-323e6831b916 |
| x-csb-sig-white-list | 请求头白名单 | 值为参与签名计算的 header key，按照ASCII 从小到大排序，多个值用 （；）分开。 | x-csb-sig-expire;x-csb- sig-scheme;x-csb-sig- timestamp |
| x-csb-sig | 签名 | 根据请求信息生成的签名结果。 | UiWshZ6PNWUGIpmm Qm2gnkHkGm5UIdkC7 sx23DTDDKs= |

以上信息除签名以外，直接填充即可，对于签名需要有以下计算流程： 请求信息格式化。 扰动请求信息。 为扰动结果生成摘要。 对摘要结果进行Base64编码，编码结果为签名。

**请求信息格式化**

请求信息中参与计算签名的有以下内容。

| 参数 | 介绍 | 格式化过程 |
|---|---|---|
| HttpMethod | 请求类型 | 全大写。 |
| HeaderWhiteList | 参与计算签名的请求头key值 | 全小写，按照字典排序升序，多个值间以（；）分隔。 |
| header | HeaderWhiteList中，key对应的 value | 先后顺序与HeaderWhiteList中的 key保持一致，多个值以 “\n" 分割，空值仍参与计算。 |
| path | 请求路径 | - |
| query | 请求参数 | 参数名称按照字典序升序，多个k-v 队以 “&” 分隔。 |
| body | 请求体 | mediatype为 application/json， 对json字符串使用md5算法获取摘要二进制数组，并将该数组做 Base64编码；mediatype 为 application/x-www-form- urlencoded ，处理方式与query相同，参数放入 query中；其余 mediatype，值为 ""。 |

获取以上信息后，需要按照以下格式进行排列：

```
HttpMethod + '\n' + HeaderWhiteList +'\n' + header +'\n' + path + '\n' + query + '\n' + body
```

例如有请求如下：

```json
curl --location --request POST 'localhost:80/test/echo' \ --header 'User-Agent: apifox/1.0.0 (https://www.apifox.cn)' \ --header 'Content-Type: application/json' \ --data-raw '{
    "id":1,
    "msg":"test"
}'
```

在经过签名处理后的格式化信息为：

```
POST x-csb-sig-expire;x-csb-sig-scheme;x-csb-sig-timestamp 60000 fwj_test 1654571140853 /test/echo ewww8tc903GK8is3nD2jTA==
```

**扰动格式化信息并为结果生成摘要**

为防止攻击人根据格式化信息与摘要算法直接碰撞出签名结果，需要用一个信息（SecretKey）去扰动原先的格式化信息。SecretKey在创建签名方案时，由后端生成。可在签名方案列表、路由详情等位置查看 SecretKey。当前支持的两种签名算法在计算签名时会进行扰动逻辑以及为结果生成摘要，所以直接调用方法即可。对于Java，可通过 javax.crypto.Mac 来根据签名算法名称获取对应的签名工具类实例。 SecretKey（签名密钥）、签名方案名称、签名算法获取方式参考为路由配置签名方案。

**说明**

在微服务架构中，会有多个服务接受来自外部客户端的请求，通常情况下，需要在网关中进行请求处理，并将其作为外部服务访问内部服务的控制点，以及对外部用户访问的请求进行身份验证。 支持API KEY、BASIC、JWT、OAuth2.0、API网关应用和CSB鉴权六种认证方式：
**JWT**（JSON Web Token）：是一个非常轻巧的规范，保证用户和服务器之间传递安全可靠的
信息。在身份认证中，获得一个JSON Web 令牌凭据。令牌的保存时间不应超过所需的时间。
**BASIC**：是一种较为简单的HTTP认证方式，客户端通过明文传输用户名和密码到服务端进行认
证，通常需要配合HTTPS来保证信息传输的安全。

**健康检查**仅在**服务类型**选择**RPC****服务**且**上游类型**选择**固定节点**，或**服务类型**选择**VPC**时显
示。

| 参数 | 描述 |
|---|---|
| 健康检查类型 | 健康检查接口的请求协议类型，包括HTTP/HTTPS、TCP协议的请求。 |
| 健康检查路径 | 健康检查的接口路径，当前支持GET类型接口，如：/health Check。 |
| HTTP请求健康状态码 | 健康检查接口的HTTP响应状态码，根据返回的状态码进行断言，断言成功则为健康状态。多个状态码可使用半角英文逗号（,）分隔，如：200,201。 |
| 请求超时（ms） | 健康检查接口请求超时时间，超时则认为该次检查失败，如 10000ms。 |
| 健康节点检查间隔（s） | 健康节点持续健康检查频率，如：10，即每10s对健康节点进行健康检查。 |
| 不健康节点检查间隔（s） | 对于不健康节点列表的检查频率，如：5，即每5s对不健康节点进行健康检查。 |
| 到健康状态的检查阈值 | 持续对不健康节点进行健康检查，当健康次数达到阈值时， 转为健康节点，如：3，即当对某一不健康节点进行持续健康检查，健康次数达到3次，将该节点状态转为健康，后续将正常负载。 |
| 到不健康状态的检查阈值 | 持续对健康节点进行健康检查，当不健康次数达到阈值时， 转为不健康节点，如：3，即当对某一健康节点进行持续健康检查，不健康次数达到3次，将该节点状态转为不健康，后续将不对其进行请求转发。 |

**说明**

服务的类型分为**固定节点**与**服务发现**，如要选择**服务发现**类型，需要完成服务来源的创建，具体操作方式请参见创建来源。 您首先需要将已有的微服务接入到平台中，提供服务调用相关信息。让网关可以获取到服务地址，然后可以对服务下的接口进行管理、路由等。 目前支持两种方式添加服务： 从注册中心添加，如果在网关中添加了注册中心作为服务来源。 固定地址添加：如果该服务没有服务发现机制，需要手动添加服务的后端节点地址。

**创建源路由**

**使用场景说明**

例如在源网关中创建一条名为“httpbin”的**源路由**后。级联网关中会自动创建一条名为 “cascadehttpbin”的**级联路由**。网络B中的用户，便可以通过该级联路由，访问网络A中的后端服务了。

**操作步骤**

**重要**

1. 登录API网关控制台。

3. 在**网关实例**页面，选择指定实例，单击实例ID或**操作**列的**详情**。
4. 在左侧导航栏，选择**级联管理** > **源路由**。
5. 单击**创建源路由**，填写以下配置项后，单击**确定**。

| 参数 | 说明 |
|---|---|
| 路由名称 | 用户自定义。 |
| 路由路径 | 与创建普通路由规则相同。 |
| 路由截取级数 | 在发送请求至下游服务之前，从请求URI中剥离的路径数量。 |
| 路由优先级 | 数值越低，路由执行的优先级越高。 |
| 请求方法/请求Header/请求 Cookie/请求Query | 支持针对请求方法、请求头，Cookie和Query请求路径的参数进行配置，只有符合匹配规则的路由才可进行流量转发。 若不指定请求方法，路由匹配时将匹配任何请求方法。 |
| 后端服务 | 与创建普通路由规则相同，数据准备请参考服务列表中创建服务或导入服务。 |
| 级联链路 | 用户需要选择级联链路，即选择将该源路由同步至哪个级联网关中。数据准备参考创建级联链路进行创建。 |

**创建完源路由后注意事项**

可以在源路由详情中查看级联路由的同步状态，**创建成功**代表该路由成功同步至级联网关中，**创建失败**则代表路由创建失败，需要通过日志查看原因。 如果同步失败的情况持续出现，可以在**级联网关**列表页编辑目标级联网关，单击**测试连接**，查看控制台是否能够成功连接级联网关控制台。如果无法成功连接，根据错误提示进行解决，在成功连接后，重新编辑源路由进行尝试；如果可以成功连接，但是仍然出现“同步失败”的情况，需要联系开发人员进行排查。 确认源路由与级联路由都正常之后，可以调用该路由以确认是否正常工作。

**说明**

为了与普通路由区分，源路由与级联路由都默认加上了 `**API`网关`_cascade:true**` 的Header匹配规则。因此，在发起请求时，必须携带该Header，才能成功匹配到对应的路由。

**PKCE能力**

**PKCE介绍**

PKCE全称是Proof Key for Code Exchange，在2015年发布，它是OAuth 2.0核心的一个扩展协议，所以可以和现有的授权模式结合使用，比如Authorization Code + PKCE，这也是最佳实践，PKCE最初是为移动设备应用和本地应用创建的，主要是为了减少公共客户端的授权码拦截攻击。在最新的OAuth 2.1规范中，推荐所有客户端都使用PKCE，而不仅仅是公共客户端，并且移除了Implicit隐式和Password模式。那么之前使用这两种模式的客户端怎么办？是的，您现在都可以尝试使用Authorization Code + PKCE的授权模式。那么PKCE为什么有这种魔力呢？实际上它的原理是客户端提供一个自创建的证明给授权服务器， 授权服务器通过它来验证客户端，把访问令牌（access_token）颁发给真实的客户端而不是伪造的。

##### 流控策略

本文将为您介绍如何配置流控策略。

**配置流控策略**

通过流控策略，可以实现对请求的限流。在创建流控策略页面，填写配置项后进行创建。 如开启了Client IP和Remote Host请求属性限流，网关将会对所有请求的IP或Host进行限流，如选择其他三种属性（Header、URL参数、Cookie），则可以对其进行具体的参数匹配，符合条件的请求才会进行限流，具体配置项说明如下：

| 参数 | 说明 |
|---|---|
| 名称 | 策略的名称，用户自定义。 |
| 作用范围 | 参考创建策略中的作用范围。支持全局和局部，选择局部时，支持绑定路由、绑定服务和绑定消费者以及任意领域对象的组合。 |
| 请求属性匹配 | 开启后，可以选择以下参数属性进行配置： Client IP：开启后会对所有客户端IP进行限流。 Remote Host：开启后会对所有客户端Host进行限流。 Header：开启后会匹配请求头参数进行限流，匹配模式支持精确、正则和子串。 URL参数：开启后会匹配URL参数进行限流，匹配模式支持精确、正则和子串。 Cookie：开启后会匹配Cookie参数进行限流，匹配模式支持精确、正则和子串。 |
| 阈值类型 | 支持QPS和线程两种类型。 |
| 请求数阈值 | 阈值类型选择QPS时显示，表示单位时间内允许经过的最大请求个数，超过该数量的请求则会被拒绝。 |
| 流控方式 | 阈值类型选择QPS时显示，支持均匀排队和快速排队。 |
| 超时时间 | 流控方式选择均匀排队时显示，请求经过时会进行排队，排队时间过长则会进行失败处理。 |
| 突发流量 | 流控方式选择快速排队时显示，表示流量突发时允许经过的最大流量，超过该流量的请求则会被拒绝。 |

请求头限流是通过检查HTTP请求头中的特定字段来限制请求的频率。您可以使用精确匹配、正则匹配或子串匹配来设置匹配规则。

**示例二：正则匹配**

如果您希望匹配所有以1开头的用户ID，您可以使用以下设置： 匹配模式：正则匹配 URL参数名称：user_id 匹配串：^1.* 这将针对所有user_id以1开头的请求进行限流。

**示例三：子串匹配**

如果您希望匹配所有包含123的用户ID，您可以使用以下设置： 匹配模式：子串匹配 URL参数名称：user_id 匹配串：123 这将针对来自包含123的用户ID的请求进行限流。

**Cookie参数限流**

Cookie限流是通过检查HTTP请求中的特定Cookie来限制请求的频率。您可以使用精确匹配、正则匹配或子串匹配来设置匹配规则。

**示例一：精确匹配**

**示例二：正则匹配**

匹配方式：正则匹配 Cookie：session_id 值：^1.* 这将针对session_id以1开头的请求限流。

**示例三：子串匹配**

##### 跨域策略

通过跨域策略，动态为接入的服务配置跨域能力。当前版本支持CORS、JSONP。

**配置跨域策略**

在创建跨域策略页面，填写配置项后进行创建。

| 参数 | 说明 |
|---|---|
| 名称 | 策略的名称，用户自定义。 |
| 作用范围 | 参考创建策略中的作用范围。支持全局和局部，选择局部时，仅支持绑定路由、绑定服务和这两个领域对象的组合。 |
| 跨域类型 | 支持CORS和JSONP。 |
| 来源 | 跨域类型选择CORS时显示，Origin，对应调用者的访问地址，由协议、域名以及端口组成，例如： http://httpbin:80.org。 |
| 请求类型 | 跨域类型选择CORS时显示，支持：GET、POST、PUT、DELETE、HEAD、PATCH和OPTIONS。 |
| 传递Cookie | 跨域类型选择CORS时显示，可选择允许或禁止，当来源为全部（填入*）时，禁止传递Cookie。 |

| 回调函数名称 | 跨域类型选择JSONP时显示，该名称对应的是请求中携带的参数。注意，回调函数名称不要与后端接口参数名称重复。 |

**跨域策略示例**

**CORS跨域**

配置内容： 允许所有来源。 不允许传递Cookie。 允许使用任何请求头。 前端只能获取CORS的响应头。

**允许请求携带Cookie**

使用场景：请求需要携带Cookie且前端服务地址明确。 配置内容： 来源中填入前端服务地址，如果有多个，则以英文半角逗号（,）分隔。 选择允许传递Cookie。

**限制允许请求携带的请求头**

使用场景：限制前端向后端发起请求时需要携带的请求头，只允许使用指定的请求头。 配置内容：Allow-Headers中填入对应的请求头，有多个则用英文半角逗号分隔（,）。

**允许前端获取自定义的响应头**

使用场景：前端需要获取响应头，且该响应头不是CORS默认允许获取的响应头（Cache-Control、 Content-Language、Content-Length、Content-Type、Expires、Last-Modified、Pragma）。 配置内容：Expose-Headers 中添加需要获取的响应头，多个值以英文半角逗号（,）分隔。

**配置预检缓存时间**

配置建议：如果需要限制请求头，且请求头参数变更频繁，不要将预检缓存时间设置过长。 对于复杂请求，浏览器会在正式发起请求前发起一次预检请求，预检通过后才会发起正式的请求。预检成功后，浏览器会缓存该预检信息（根据URL和请求头参数匹配），当再次发起同样的请求时，就不需要再进行预检。由于预检信息是缓存在浏览器中，修改CORS配置后，如果浏览器已经有请求的预检缓存，在缓存失效前，仍不会发起预检请求，对于Allow-Headers的配置就不会生效。

**JSONP跨域**

后端某一个接口直接请求的URL为：http://test.com/hello?id=1&msg=1 前端想向后端发起一个JSONP请求，回调函数参数为Callback，前端设置的会调函数值为JSONP，那么请求为：http://test.com/hello?id=1&msg=1&callback=jsonp。

**选择CORS还是JSONP**

如果仅使用get ajax请求，并且需要支持**IE <= 9**，**Opera <12**或**Firefox <3.5**或其他各种较旧的浏览器，使用JSONP，否则使用CORS。

##### 缓存策略

开启响应缓存策略后可为指定接口缓存响应信息，之后匹配到的请求可直接使用缓存的响应信息，而不需要再去请求服务，以减少服务处理请求的压力。

**配置缓存策略**

响应信息可根据请求的请求类型（Method），请求路径（Path），请求头（Headers），请求参数 （QueryParams）进行区分，参数和值不同，则响应不同。

| 参数 | 说明 |
|---|---|
| 名称 | 策略的名称，用户自定义。 |
| 作用范围 | 参考创建策略中的作用范围。支持全局和局部，选择局部时，支持绑定路由、绑定服务和绑定消费者以及这三个领域对象的任意组合。 |
| 缓存策略 | 根据实际使用场景进行配置，可参考缓存策略配置示例。 |

**缓存策略配置示例**

**关闭缓存控制**

需要为服务A的某一接口添加响应缓存，直连服务A请求该接口的URL为：

```
GET http://testA.com/hello?id=1&msg=1
```

配置信息为以下：
**缓存时间**：300秒。
**缓存控制**：关闭。
**响应状态码**：200。
**缓存接口**：**Method**选择 `GET` ，**Path**填写 `/hello` ，QueryParams填写 `id,msg` 。

**开启缓存控制**

使用cache-control指定缓存使用方式。 开启**缓存控制**后，可在请求头中添加Cache-Control指令，为请求指定缓存使用方式。 当前支持以下指令： no-store : 不使用缓存。 max-age: 设置接受多少时间内的缓存响应信息，单位为秒。例如 max-age=2 则请求只使用写入缓存后2秒内的响应信息，超过则不进行使用。 使用示例如下：

```bash
curl --request GET 'http://domain/cache/hello' --header 'cache-control: no-store' curl --request GET 'http://domain/cache/hello' --header 'cache-control: max-age=300'
```

##### IP黑白名单策略

## 级联管理

### 概述

级联是API网关提供的一个重要特性，它提供了一种多个API网关之间协作的方式，从而打通多个API网关之间的路由和服务，使得一个API网关用户可以调用到另一个API网关管理的服务。

**功能背景**

级联功能主要用于打通两个网络分区（两套API网关）中的路由和服务，使得一个网络分区中的用户可以通过API网关调用另一个网络分区中的服务，适用于跨地域大型专有云系统。 试想如下场景：企业内部拥有两套独立的环境（例如两套独立的专有云系统），两套环境处于不同的网络分区之中（网络A和网络B），并各自部署了一套API网关系统。日常使用过程中，用户通过API网关暴露本环境下的后端服务，供本环境下的用户进行调用，两套系统之间互不干涉。 现在，我们有了进一步的需求：我们希望网络A中的后端服务可以通过API网关，使用路由的方式发布至网络 B中，供网络B中的用户进行调用，从而使得两个环境中的服务可以灵活互通，那么此时使用我们提供的“级联功能”，就可以很方便地达到这个目的。

**基本概念**

上述示意图包含了级联功能中的主要概念以及使用级联的主要流程，下面介绍其中的基本概念： 源网关：用户想要暴露的后端服务所在网络的网关。例如，上述示意图中，是网络A中的后端服务想要暴露给网络B中的用户使用，那么网络A中的API网关被称为“源网关”。 级联网关：想要调用后端服务的用户所在网络的网关。例如，上述示意图中，如果网络B中的用户想要调用网络A中的后端服务，那么网络B中的API网关被称为“级联网关”。 源网关控制台：网关所在的控制台。用户在源网关控制台创建路由、消费者、签名等实体，这些实体会被同步至级联网关中。用户也可以对这些实体进行修改、删除等操作，这些操作同样会被同步至级联网关中。源网关控制台可以理解为“操作方”。 级联网关控制台：级联网关所在的控制台。该控制台负责接受源网关控制台传来的创建路由、消费者、实体等请求，并同步创建相应的级联实体。级联网关控制台可以理解为“接受方”，只能接受源网关控制台传来的命令并执行。 用级联功能的前提条件： 多套API网关的版本均要求不低于2.5.1。 源网关控制台和级联网关控制台之间的网络需要打通，即源网关控制台需要能够访问到级联网关控制台。 源网关和级联网关之间的网络需要打通，即级联网关需要能够访问到源网关。 在使用级联功能时，用户需要依次执行如下步骤：
1. 导入级联网关。用户需要在源网关控制台中导入级联网关，填写其基本信息。导入完成后，用户可以在源
网关控制台上观察到级联网关的状态。
2. 创建级联链路。用户需要在源网关控制台中创建级联链路，级联链路包含源网关和级联网关，其中源网关
需要为本控制台下管理的网关实例，级联网关需要是第一步中导入的级联网关。
3. 创建路由。用户需要在源网关控制台中创建源路由，并指定级联链路。创建完毕后，会自动在级联网关中
创建一条相应的级联路由。 执行以上步骤后，基本目的已经可以实现，网络B中的用户已经可以通过级联路由，访问到网络A中的服务了。 如果对鉴权和签名等策略有需求，还可以执行以下步骤：
1. 创建源消费者。用户可以在源网关控制台中创建源消费者，并指定级联链路。创建完毕后，会自动在级联
网关中创建一个级联消费者。需要注意的是，在对源消费者绑定路由时，只能绑定级联链路相同的路由。
2. 创建源签名。用户可以在源网关控制台中创建源签名，并指定级联链路。创建完毕后，会自动在级联网关
中创建一个级联签名。需要注意的是，在对源路由创建签名策略时，只能绑定级联链路相同的源签名。

| 参数 | 描述 |

|---|---|
| 后端接口路径 | 网关请求到您的后端的请求路径。 |
| 映射模式 | 该接口所采用的映射模式，一共有三种。 入参透传：该模式下接口定义仅作文档使用，网关不会对该接口进行任何校验与映射操作。 入参映射（过滤未知参数）：该模式下，网关在接受到请求后将过滤掉未在接口中定义的参数，如您在接口中定义了query参数a和b，但在请求时候，请求参数为a=1&b=2&c=3，网关将c=3过滤，转发到您后端的真实参数为a=1&b=2。 入参映射（透传未知参数）：与上一模式相反，在该模式下，对于未在接口中定义的参数，网关不对其做校验、过滤和映射的操作，而是原封不动地传递到您的后端。 |
| 请求参数 | 根据实际需要配置Params、Body、Header页签的参数。更多说明请参考请求参数。 |

**请求参数**

在请求参数一栏，您可以定义该接口对应的请求参数。请求参数一共由四个位置构成。 Query：以?a=&b=的形式拼接在URL后面的参数。 Path：拼接在请求path中的参数。 Body：请求体。 Header：请求头。 定义请求参数时，您可以指定映射到后端的某位置。 单击**编辑更多**，您还可以让网关对该参数进行一定校验限定。

**常量参数**

在请求时您可以不携带一些固定的参数，将其定义为常量参数，此时网关会自动为您加上这些参数。目前常量参数仅支持query和header位置。

**返回响应**

您可以定义后端响应内容，但是该部分仅作文档展示作用。

## 网关日志

本文介绍如何为网关配置日志采集、日志的分类，以及主要日志的示例和具体说明。

**配置日志采集**

当网关基于 EDAS 部署时，您可将日志采集到 SLS 中。步骤及参数配置如下： 首先，请在实例列表中找到需要配置日志采集的网关实例，并跳转到关联的 EDAS 应用中。之后通过 EDAS 的应用部署，便可以进行日志采集设置。 采集日志类型：文件日志（容器日志路径） 采集路径：/home/admin/cop-broker/logs/*.log 配置完成后，您可以在 SLS 中按分类查看采集到的网关日志：

**日志分类**

采集到的日志分为如下几类：

| 日志名称 | 详情描述 |
|---|---|
| access.log | 网关请求日志，默认打开，记录每一个请求。 |

| request.log | 网关的请求体/响应体日志，默认关闭，记录每一个请求的请求体和响应体。 出于性能考虑，默认关闭此日志。开启时，因为会对所有的请求和响应进行解包，网关性能会急剧下降。 说明还请注意 access.log 与 request.log 的区别。access.log 仅关注请求的 URI 信息，并不会尝试读取报文体，主要对每一条请求进行记录；而 request.log 常用于定位业务问题，需要查看具体的报文体。 |
|---|---|
| config.log | 网关的配置推送日志。每次收到配置中心推送时，打印出配置内容，用于定位配置推送问题。 |
| schedule.log | 定时任务的运行日志。为了避免定时任务的日志干扰其他日志的输出，单独使用该文件记录定时任务的日志。 |
| remoting.log | 连接日志。记录网关与后端服务的长连接建立与断开的日志，用于排查网络问题。 |
| debug.log | 网关的业务日志。其余的业务信息都会被输出到这个日志里。 |
