# 容器服务Kubernetes版 容器计算服务ACS 用户指南

容器服务Kubernetes版 CS

## 什么是容器计算服务 ACS

容器计算服务 ACS是面向专有云环境的Serverless容器算力服务，用于以Pod为算力单元提供GPU容器计算资源，无需管理节点即可运行容器化工作负载。

**背景与挑战**

随着企业数字化转型深入推进，越来越多的组织在专有云环境中部署容器化应用和AI工作负载。传统容器服务要求用户预先规划节点容量、管理虚拟机生命周期、处理操作系统升级和集群组件维护，运维复杂度高。 在AI Agent场景中，应用对安全隔离和弹性速度提出了更高要求——Agent运行时需要执行不可信代码，需要严格的安全沙箱隔离；模型动态控制工具执行会产生大规模秒级弹性并发，传统节点级扩容方式难以满足。同时，GPU算力在多租户环境下的规格化切分和按需分配也缺乏有效手段。

**产品概述**

容器计算服务 ACS是基于Kubernetes的Serverless容器计算服务，面向专有云环境提供GPU容器算力。 ACS以Pod作为算力交付单元，用户无需进行容量规划和节点运维，直接提交Pod即可获得容器算力资源。 产品支持GPU型和高性能网络GPU型等实例类型，GPU Pod最小支持1卡GPU。ACS默认采用安全沙箱技术实现Pod级别的强隔离，每个Pod运行在独立内核中，不存在资源争抢。弹性方面，ACS支持秒级Pod级弹性伸缩，适配突发流量和AI推理等场景。产品兼容标准Kubernetes API，支持kubectl连接和YAML部署， 同时兼容E2B等AI Agent生态协议，为Agent应用提供安全沙箱运行环境。

**核心功能列表**

**Serverless****容器算力**：以Pod为算力交付单元，无需节点运维和容量规划，支持GPU型实例类型，按量
秒级计费。
**安全沙箱隔离**：基于轻量级安全沙箱技术，每个Pod运行在独立内核中，实现计算、网络、存储多维度的
强隔离。
**秒级弹性伸缩**：支持Pod维度的秒级弹性伸缩，集成HPA和AHPA预测伸缩策略，适配突发流量场景。
**GPU****容器算力**：支持多种GPU卡型，面向AI训练推理和异构计算场景，提供灵活的vCPU/内存/GPU配
比。
**Kubernetes****生态兼容**：兼容标准Kubernetes API，支持kubectl、YAML部署，集成Prometheus监
控和SLS日志采集。 容器服务Kubernetes版

#### 连接集群

创建ACS集群后，您可以通过kubectl命令行工具连接集群，进行应用部署、资源管理和运维操作。本文介绍如何获取集群的连接信息并连接集群。

**背景信息**

通过获取集群的KubeConfig配置文件，在本地计算机上使用kubectl命令行工具连接集群。适用于日常运维、自动化脚本和CI/CD流水线等场景。

**前提条件**

已安装kubectl命令行工具（仅KubeConfig方式需要）。

**操作步骤**

1. 登录容器计算服务 ACS控制台。
2. 在左侧导航栏选择**集群**。
3. 在**集群列表**页面，单击目标集群名称或**操作**列的**详情**，进入**集群信息**页面。
4. 单击**连接信息**页签。
5. 在KubeConfig区域，单击**复制**按钮，复制KubeConfig配置内容。
6. 在本地计算机的 ~/.kube/config 文件中，将复制的内容粘贴并保存。

**说明**

如果 ~/.kube/config 文件不存在，请创建该文件。
7. 执行以下命令验证连接是否成功：

```bash
kubectl get nodes
```

如果返回集群节点信息，说明连接成功。

**重要**

KubeConfig包含集群访问凭证，请妥善保管，避免泄露。 容器服务Kubernetes版

#### 升级集群

ACS基于社区版Kubernetes开发，仅发布Minor版本号为双数的K8s版本（如1.30、1.32等），并为每个 K8s Minor版本提供为期两年的维保周期（自发布日起）。当新的K8s版本发布后，您可以将集群升级到新版本，以获得最新的功能特性和安全补丁。本文介绍如何升级ACS集群的Kubernetes版本。

**注意事项**

升级操作不可回滚，请在升级前做好充分评估。 建议在业务低峰期进行升级操作。 升级前建议备份重要应用数据。 确保集群当前版本运行稳定，无异常事件。

**操作步骤**

**全部升级**

1. 登录容器计算服务 ACS控制台。
2. 在左侧导航栏选择**集群**。
3. 您可以通过以下两种方式进入**集群升级**页面：
方式一：在**集群列表**页面，单击目标集群**操作**列的 ，选择**集群升级**。 方式二： a. 在**集群列表**页面，单击目标集群名称或**操作**列的**详情**，进入**集群信息**页面。 b. 在左侧导航栏，选择**运维管理** > **集群升级**。
4. 在**手动升级**页面，配置以下参数，然后单击**升级前置检查**。

| 参数 | 说明 |
|---|---|
| 当前版本 | 展示当前集群的版本。 |
| 目标版本 | 选择可升级的集群版本。 |
| 升级模式 | 选择全部升级。 |
| 升级策略 | 设置每批次的最大并行数。 |

5. 检查完成后，单击**查看详情**，查看检查报告。
**检查结果**为**正常**时，您可以继续进行集群升级操作。

#### 创建任务工作负载Job

Job主要用于运行短暂的、一次性的批量任务（short-lived one-off tasks），确保批处理任务的一个或多个Pod成功执行。ACS集群支持通过控制台创建任务类型的应用，本文介绍如何创建一个Job类型工作负载。

**背景信息**

容器服务Kubernetes版 Job是Kubernetes中用于运行一次性任务的工作负载类型。Job会创建一个或多个Pod来执行任务，确保指定数量的Pod成功完成后终止。适用于数据处理、批量计算、CI/CD流水线等短时任务场景。ACS采用 Serverless K8s架构，Pod即实例，您无需管理底层节点，Job创建的Pod对应ACS容器算力实例。 根据 `.spec.completions` （需要成功完成的Pod数，默认为1）和 `.spec.parallelism` （Job可以并行运行的最大副本数，默认为1）的配置，可以将Job划分为以下几种类型：

| Job类型 | completions | parallelism | 使用示例 | 行为 |
|---|---|---|---|---|
| 一次性Job | 1 | 1 | 数据库迁移。 | 运行一个Pod直至其成功完成。 |
| 固定结束次数的Job | 2+ | 1 | 处理工作队列的 Pod。 | Pod依次运行，直至成功完成的Pod数达到 completions 配置的数量。 |
| 带有工作队列的并行Job | 1 | 2+ | 多个Pod同时处理工作队列，不要求成功数。 | 多个Pod并行运行， 直至有一个Pod成功完成。 |
| 固定结束次数的并行Job | 2+ | 2+ | 多个Pod同时处理工作队列，要求成功数。 | 多个Pod并行运行， 直至成功完成的Pod 数达到 completions 配置的数量。 |

#### 创建定时任务工作负载CronJob

定时任务CronJob用于创建周期性以及重复性的任务，例如执行备份操作或者发送邮件。Job负责批量处理短暂的一次性任务，即仅执行一次的任务，而CronJob则是在Job基础上增加了时间调度。本文介绍如何创建定时任务CronJob。

**背景信息**

容器服务Kubernetes版 CronJob是Kubernetes中用于按时间调度运行周期性任务的工作负载类型。CronJob根据Cron表达式定时创建Job，适用于定期备份数据、发送报告、数据清理、日志归档等周期性任务场景。ACS采用Serverless K8s架构，完全兼容Kubernetes CronJob，您无需管理底层节点，每次定时触发的Job中的Pod对应ACS容器算力实例。

#### ACS Pod实例生命周期

本文主要介绍ACS Pod实例的生命周期状态、终态保留策略、生命周期钩子和相关说明。

**背景信息**

了解ACS Pod实例的生命周期，有助于您掌握Pod从创建到终止的各个阶段，合理配置健康检查、生命周期钩子和优雅终止策略，保障应用的稳定运行。ACS Pod遵循Kubernetes标准的Pod生命周期，同时提供 Serverless形态下的特殊行为。

**Pod生命周期状态**

Pod在整个生命周期中会经历以下状态：

| 状态 | 说明 |
|---|---|
| Pending | Pod已被提交，但尚未被调度或正在拉取镜像。 |
| Running | Pod已绑定到节点，所有容器已创建，至少有一个容器正在运行。 |

容器服务Kubernetes版

| Succeeded | Pod中的所有容器均已成功终止，且不会重启。 |
|---|---|
| Failed | Pod中的所有容器均已终止，且至少有一个容器非正常退出。 |
| Unknown | 无法获取Pod的状态，通常是与节点通信失败。 |

关于ACS Pod实例生命周期的详细内容，请参见Kubernetes官方文档Pod的生命周期。

**终态Pod保留策略**

当ACS Pod实例运行终止后，底层计算资源将会被回收。随Pod实例一起创建的其他资源（例如EIP等）默认随Pod实例一起释放。 终态（处于Failed、Succeeded状态）Pod实例的元数据信息的保留情况如下： 30分钟内的Pod实例信息全部保留。 超出30分钟的Pod实例仅保留最近的100条（单个地域分别计算）。

**说明**

如需长期保留Pod的运行记录，建议配置日志采集到阿里云日志服务SLS。

**Pod实例生命周期钩子**

ACS Pod实例支持标准的Kubernetes Pod生命周期钩子，如postStart和preStop，允许您在容器生命周期的关键节点执行自定义脚本。

**postStart钩子**

容器创建后立即执行。适用于容器启动后的初始化操作，如预热缓存、加载配置等。

```
lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "echo 'Container started' > /tmp/poststart.log"]
```

在使用postStart钩子时，请特别注意以下行为： postStart Hook的执行与容器主进程的启动是异步的，当ACS Pod实例的容器PostStart Hook长期执行未结束时，会阻塞容器进入Running状态。 当ACS Pod实例的容器PostStart Hook执行期间，如果发起删除Pod操作，Pod也无法及时响应删除。

**说明**

postStart钩子的行为由Kubernetes原生机制决定。请您务必确保在钩子中执行的命令或脚本是快速、非阻塞的，并能正常退出。 对于用户自定义钩子配置不当（如执行时间过长、无法退出等），导致的Pod启动延迟、删除失败、资源无法释放等问题，需要由用户自行排查。 关于postStart Hook的详细内容，请参见Kubernetes官方文档容器生命周期回调。

**preStop钩子**

容器服务Kubernetes版容器终止前执行。适用于容器停止前的清理操作，如优雅关闭连接、保存状态等。

```
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5 && echo 'Container stopping'"]
```

**说明**

preStop钩子执行期间，Pod仍处于Terminating状态。钩子执行完成或超时后，容器才会被终止。

**重要**

如果postStart钩子执行失败，容器可能会被终止并重启。建议为preStop钩子设置合理的超时时间， 避免阻塞Pod的优雅终止流程。

**优雅终止**

Pod删除时，系统会发送SIGTERM信号，并等待 `terminationGracePeriodSeconds` （默认30秒）后发送SIGKILL强制终止。

```
spec:
  terminationGracePeriodSeconds: 60
```

**说明**

如需更长的优雅终止时间，请调整 `terminationGracePeriodSeconds` 的值。

**重要**

如果容器未能在 `terminationGracePeriodSeconds` 内完成终止，系统将强制终止容器，可能导致数据丢失。

### 网络

#### 网络概述

容器计算服务 ACS集成Kubernetes网络、VPC、SLB，提供稳定高性能的容器网络。本文介绍ACS集群网络及网络底层基础设施的重要概念，如容器网络、Service、Ingress、提供服务发现能力的DNS等。您可以通过了解这些概念，更合理地设计应用部署模型和网络访问的方式。

**ACS常见网络能力一览表**

| 分类 | 常见网络能力 | 功能支持 | 说明 |
|---|---|---|---|
| 网络配置管理 | Pod维度网络配置 | 支持 | 为Pod指定交换机和安全组。 |
| 网络配置管理 | 设置Pod安全组 | 支持 | 为Pod指定安全组规则。 |

容器服务Kubernetes版

| 南北向访问 | Pod访问公网 | 支持 | 为集群开启公网访问能力，或通过配置注解为 Pod挂载EIP。 |
|---|---|---|---|
| 南北向访问 | 从公网直接访问Pod | 支持 | 通过配置注解为Pod挂载 EIP。 |
| 南北向访问 | 使用LoadBalancer服务 | 支持 | 通过SLB将服务暴露到公网或VPC内网。 |
| 南北向访问 | 使用Ingress | 支持 | Nginx Ingress管理。 |

由于云原生的应用通常需要敏捷的迭代和快速的弹性，且单一容器和其相关的网络资源的生命周期非常短暂，所以需要固定的访问地址，以及自动负载均衡实现快速的业务弹性。ACS采用Service方式为一组容器提供固定的访问入口，并对这一组容器做负载均衡。实现原理如下： 创建Service对象时，ACS会分配一个相对固定的Service IP地址。 通过字段 `selector` 选择一组容器，以将这个Service IP地址和端口负载均衡到这一组容器的IP和端口上。 Service网络支持以下多种模式，分别对接不同来源和类型的客户端的访问：

**ClusterIP**

ClusterIP类型的Service用于集群内部的应用间访问。如果您的应用需要暴露到集群内部提供服务，需使用ClusterIP类型的Service来暴露。 说明：创建Service时默认的Service类型为ClusterIP。

**LoadBalancer**

LoadBalancer类型的Service同样是将集群内部部署的应用向外暴露，不过它是通过SLB（负载均衡） 进行暴露的，相对于NodePort方式，有更高的可用性和性能。关于如何通过LoadBalancer类型Service

**Headless Service**

Headless Service类型的Service是在Service属性中指定 `clusterIP` 字段为 `None` 。采用 Headless Service类型后，Service将没有固定的虚拟IP地址，客户端访问Service的域名时会通过DNS 返回所有的后端Pod实例的IP地址，客户端需要采用DNS负载均衡来实现对后端的负载均衡。

**ExternalName**

ExternalName类型的Service将集群外部的域名映射到集群内部的Service上，例如将外部的数据库域名映射到集群内部的Service名，那么就能在集群内部通过Service名直接访问。

**重要**

ACS不支持NodePort类型的Service和Session Affinity（会话保持）功能。如需从集群外部访问服务，请使用LoadBalancer类型的Service。 在ACS集群中，与Service的四层负载均衡不同，Ingress是集群内Service对外暴露七层的访问接入点。您可以通过Ingress资源来配置不同的七层转发规则，例如通过域名或者访问路径来路由到不同的Service上， 从而达到七层的负载均衡作用。 容器服务Kubernetes版 ACS支持Nginx Ingress作为Ingress控制器，提供高性能的七层流量分发能力。更多信息，请参
**示例**：常见的前后端分离的架构方式中，前后端的访问地址分别使用不同的访问路径。对应这种场景，可以
采用Ingress，根据七层的访问路径负载到不同的应用实例上。

**服务发现DNS**

ACS使用DNS来实现应用的服务发现能力，例如客户端应用可以通过Service的服务名解析出它的ClusterIP 访问，也可以通过StatefulSet的Pod名解析出Pod的IP地址。采用DNS服务发现的能力让集群中应用间的调用与IP地址和部署环境相解耦。 集群的CoreDNS会将Service名自动转换成对应的Service的IP地址，来实现不同部署环境中同样的访问入口。CoreDNS支持以下解析规则：
**集群内****Service****解析**：自动为每个Service创建DNS记录，格式为 `<service-name>.`

```xml
<namespace>.svc.cluster.local 。
```

**Headless Service****解析**：返回后端所有Pod的IP列表。
**外部域名解析**：通过forward插件将外部域名查询转发到上游DNS服务器。

**网络底层基础设施**

**VPC**

VPC（Virtual Private Cloud）是基于阿里云创建的自定义私有网络，不同的专有网络之间彻底逻辑隔离。您可以在专有网络内创建和管理云产品实例，例如云服务器、云数据库RDS版和负载均衡等。每个 VPC至少由三部分组成：私网网段、交换机和路由表。

**SLB**

SLB（Server Load Balancer）通过设置虚拟服务地址，将添加的ECS实例虚拟成一个高性能、高可用的应用服务池，并根据转发规则，将来自客户端的请求分发给云服务器池中的ECS实例。 负载均衡默认检查云服务器池中的ECS实例的健康状态，自动隔离异常状态的ECS实例，消除了单台ECS 实例的单点故障，提高了应用的整体服务能力。此外，负载均衡还具备抗DDoS攻击的能力，增强了应用服务的防护能力。 负载均衡由以下三个部分组成：
**负载均衡实例**：一个负载均衡实例是一个运行的负载均衡服务，用来接收流量并将其分配给后端服务
器。
**监听**：监听用来检查客户端请求并将请求转发给后端服务器。监听也会对后端服务器进行健康检查。
**后端服务器**：一组接收前端请求的ECS实例。您可以单独添加ECS实例到服务器池，也可以通过虚拟服
务器组或主备服务器组来批量添加和管理。

**网络规划建议**

**交换机地址池**：根据预期的Pod数量选择合适的交换机CIDR范围，建议预留2倍以上的IP地址。由于每个
Pod占用一个弹性网卡资源，规划交换机地址池时需预留足够的IP地址空间，避免IP资源耗尽导致Pod创建失败。
**Service CIDR**：Service CIDR创建成功后不能修改。Service地址只在Kubernetes集群内使用，不能
和虚拟交换机地址段重叠。
**Service****规划**：优先使用ClusterIP进行内部通信，仅在需要外部访问时使用LoadBalancer。
**安全组**：通过VPC安全组规则控制Pod的入站和出站流量，实现网络级别的访问控制。

#### Service管理

本文介绍如何在ACS集群中创建和管理Service，以及通过Annotation配置负载均衡的相关操作。

**背景信息**

容器服务Kubernetes版 Service是用于暴露应用服务的核心资源对象。在容器计算服务 ACS中，Service为后端Pod提供稳定的访问入口和负载均衡能力，即使后端Pod发生变更（如扩缩容、重启），Service的访问地址保持不变。 ACS支持ClusterIP和LoadBalancer两种主要Service类型。ClusterIP用于集群内部服务通信，LoadBalancer通过SLB将服务暴露到VPC内网或公网。 重要：ACS不支持NodePort类型的Service和Session Affinity（会话保持）功能。如需从集群外部访问服务，请使用LoadBalancer类型的Service。

**前提条件**

集群中有运行中的Pod作为Service后端。 如需使用LoadBalancer Service，集群所在地域需支持SLB服务。

**Service类型说明**

| Service类型 | 访问范围 | 底层实现 | 适用场景 |
|---|---|---|---|
| ClusterIP | 集群内部 | 虚拟IP | 微服务间内部通信 |
| LoadBalancer | 公网或VPC内网 | SLB负载均衡 | Web应用、API接口对外暴露 |
| Headless Service | 集群内部 | 无虚拟IP，DNS返回Pod IP | 客户端自行负载均衡、 StatefulSet |
| ExternalName | 集群内部 | CNAME映射 | 集群内服务访问外部域名 |

**背景信息**

    spec:

      - name: my-container
        image: nginx:latest
        env:
        - name: APP_CONFIG
          valueFrom:
            configMapKeyRef:
              name: my-config
              key: log_level
```

**通过数据卷挂载**

容器服务Kubernetes版在创建工作负载时，在**数据卷**配置区域添加配置项类型的存储卷，将配置项挂载到容器的指定目录中。

apiVersion: apps/v1 kind: Deployment metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-container
        image: nginx:latest
        volumeMounts:
        - name: config-volume
          mountPath: /etc/config
      volumes:
      - name: config-volume
        configMap:
          name: my-config
```

挂载后，配置项中的每个键值对将作为目录下的一个文件，文件名为键名，文件内容为键值。例如，上述配置将生成 `/etc/config/app.conf` 和 `/etc/config/log_level` 两个文件。

```
apiVersion: apps/v1 kind: Deployment metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-container
        image: nginx:latest
        volumeMounts:
        - name: secret-volume
          mountPath: /etc/secrets
          readOnly: true
      volumes:
      - name: secret-volume
        secret:
          secretName: my-secret
```

### 存储

#### 存储概述

ACS的容器存储功能基于Kubernetes容器存储接口（CSI），融合APFS文件系统等云存储服务，并兼容 Kubernetes原生的EmptyDir、ConfigMap等存储。本文主要介绍ACS支持的云存储服务，包括各类存储服务的特点、应用场景、挂载方式等。

**存储基础知识**

**Volume**

容器中的文件在磁盘上是临时存放的，这给容器中运行的应用程序带来一些问题： 当一个Pod同时运行多个容器时，无法在这些容器之间共享文件。 当容器崩溃时，容器重建不会保留容器运行过程中产生的文件，这将导致文件丢失。 对于上述问题，Kubernetes抽象出了**Volume**（数据卷）来实现共享存储、持久化存储等能力。 Volume是Pod的一部分，只能在Pod中定义，不能独立创建。Pod中的所有容器都可以使用Volume，但需要将Volume挂载到容器中的目录下。 Volume是Pod与外部存储设备进行数据传递的通道，也是Pod内部容器之间、Pod与Pod之间、Pod与外部环境进行数据共享的方式。 Volume有多种类型，例如EmptyDir、ConfigMap、PersistentVolumeClaim（PVC）等。 更多信息，请参见Volume。

**PV与PVC**

并非所有的Volume都具有持久化特性，为了实现持久化的存储，容器存储需依赖于一个远程存储服务，为此Kubernetes引入了PV和PVC两个资源对象，来定义和使用存储资源。
**PV**（PersistentVolume，存储卷）
容器服务Kubernetes版 PV用于存储持久化数据，是一种抽象的存储卷，可以是网络存储、云存储等。PV可以由集群管理员提前创建，也可以通过SC（StorageClass，存储类）动态创建。PV独立于Pod存在，可以被多个Pod共享。
**PVC**（PersistentVolumeClaim，存储声明）
PVC表达的是用户对存储的请求，它指定了Pod需要的PV的容量大小和访问模式。PVC与PV是一一对应关系，在Pod中使用Volume关联PVC，即可让Pod使用到存储资源。 更多信息，请参见Persistent Volumes和Storage Classes。

**挂载云存储**

**存储插件**

CSI是当前Kubernetes社区推荐的存储插件实现方案，ACS提供了csi-provisioner作为ACS集群的CSI插件，支持基于云存储资源的存储卷。

**重要**

在存储卷的挂载、卸载、创建、删除等操作上，CSI插件需要您授予其访问其他产品资源的权限。

**挂载方式**

通过PV描述云存储资源（如APFS文件系统等），通过PVC绑定PV，然后在Pod的Volume中声明要使用的 PVC，可以实现挂载云存储。根据云存储资源对应PV在创建方式上的差异，挂载云存储的方式可以分为以下两种：

**静态**

根据已有的云存储资源创建PV（即静态存储卷），在PVC中直接绑定PV，以此可以实现静态挂载。该方式可以保证PV在容器启动前已经就绪，适用于已有存储资源的场景。

**动态**

通过StorageClass定义要动态创建的云存储资源，在PVC中关联StorageClass，系统会根据PVC和 StorageClass的配置，自动创建并绑定PV（即动态存储卷），以此可以实现动态挂载。该方式无需提前创建PV，更加灵活和自动化。 存储卷的挂载操作参考如下：

本文主要介绍集群检查的功能说明和使用方法。容器智能运维平台提供集群检查能力，您可以在集群升级、 迁移等操作前执行集群检查，确认集群是否符合要求，并根据检查结果进行针对性修复。

**背景信息**

集群检查是保障集群稳定性和升级成功率的重要手段。在执行集群升级、集群迁移、组件安装或组件升级等操作前，系统会自动触发检查，只有检查通过后才能继续执行变更操作。您也可以手动执行集群检查，无需输入任何参数即可对集群资源、集群组件及集群配置进行全面检查并获得相应的优化建议。 建议您定期对集群进行检查和维护，预防集群安全风险。

**前提条件**

已获取集群的访问权限。

**操作步骤**

**执行集群检查**

集群升级检查、组件检查、集群迁移检查的操作类似。下文以集群升级检查为例，介绍如何使用集群检查功能。
1. 登录容器计算服务 ACS控制台。
2. 在左侧导航栏选择**集群**。
3. 在**集群列表**页面，单击目标集群名称或**操作**列的**详情**，进入**集群信息**页面。
4. 在左侧导航栏，选择**运维管理** > **集群检查**。
5. 单击**执行升级检查**。
6. 在**升级检查**面板，选择目标集群版本，仔细阅读注意事项，选中**我已知晓并同意**，单**击执行检查**。
在**升级检查**页面，您可以查看检查概览，也可以单击**查看详情**，在**检查报告**页面查看集群升级检查的进度。

**查看检查结果**

检查任务完成后，在**检查报告**页面，根据检查报告提示进行相应处理。 容器服务Kubernetes版检查结果主要分为以下几个状态：
**正常**：无需处理，检查项通过。
**警告**：需要确认，可能引起集群异常的情况需要处理。
**异常**：需要尽快处理，否则可能导致集群无法正常工作。
针对单项检查结果，可以单击状态颜色框，查看检查对象信息及具体检查结果。检查结果包含检查异常内容、可能影响以及推荐的修复方案。您可以参考异常影响及修复方案酌情处理。

### 安全管理

#### 角色

本文主要介绍角色的功能说明和操作步骤。通过角色（RBAC）功能，您可以基于Kubernetes的角色访问控制机制，为不同组织成员配置不同的集群资源操作权限，降低账号安全风险。

**背景信息**

RBAC（Role-Based Access Control）是基于角色的访问控制。在Kubernetes中，RBAC通过Role、 ClusterRole、RoleBinding和ClusterRoleBinding等对象来管理对Kubernetes API资源的访问权限。 在专有云环境中，ACS集群使用**组织**/**资源集**进行权限管理，而非公共云的RAM用户/RAM角色机制。您可以通过组织/资源集管理成员的访问权限，并结合Kubernetes原生的RBAC机制，为不同角色成员配置不同的集群内Kubernetes资源操作权限。

**权限策略说明**

Kubernetes RBAC中，Role和ClusterRole包含一组代表相关权限的规则：
**Role**：用于在某个命名空间内设置访问权限。
**ClusterRole**：用于为集群范围的资源定义访问权限。
您可自行编写权限策略，或通过控制台创建自定义策略。

**预置角色说明**

ACS提供了以下预置角色，满足不同场景的权限管理需求： 容器服务Kubernetes版

| 预置角色 | 集群内RBAC权限 |
|---|---|
| 管理员 | 对集群所有命名空间下 Kubernetes 资源的 RBAC 读写权限，对集群存储卷、命名空间、配额的读写权限。 |
| 只读管理员 | 对集群所有命名空间下 Kubernetes 资源的 RBAC 只读权限。 |
| 运维人员 | 对集群所有命名空间下控制台可见 Kubernetes 资源的 RBAC 读写权限，对集群存储卷、命名空间、配额的只读权限。 |
| 开发人员 | 对集群所有命名空间或所选命名空间下控制台可见 Kubernetes 资源的 RBAC 读写权限。 |
| 受限用户 | 对集群所有命名空间或所选命名空间下控制台可见 Kubernetes 资源的 RBAC 只读权限。 |
| 自定义 | 权限由所选择的 ClusterRole 决定，请确认 ClusterRole 对各类资源的操作权限后再授权。 |

**重要**

用户被授予cluster-admin权限后，在该集群内可视为与主账号有相同权限的超级账号，拥有操作集群内所有资源的任意权限，请务必谨慎授权。

**前提条件**

已在专有云环境中完成组织/资源集的创建和成员分配。

  resources:
  - pods
  verbs:
  - create
  - delete
  - deletecollection
  - get
  - list
  - patch
  - update
  - watch

#### 集群审计

集群审计功能基于阿里云日志服务（SLS），为Kubernetes集群中的应用访问提供安全的审计日志记录与合规性检查。

**背景信息**

审计（Auditing）产生于API Server内部，用于记录对Kubernetes API的请求以及请求结果。ACS集群提供API Server的审计日志，帮助集群管理人员排查“什么人在什么时间对什么资源做了什么操作”，可用于追溯集群操作历史、排查集群故障等，降低集群安全运维压力。 专有云ACS集群的API Server审计功能与公共云一致，支持以下能力：
**审计日志记录**：自动记录所有对Kubernetes API的请求，包括请求来源、操作类型、目标资源、请求结
果等信息。
**审计报表**：内置4个审计日志报表，包括审计中心概览、资源操作概览、资源操作详细列表以及
Kubernetes CVE安全风险。
**告警配置**：支持对特定资源操作进行实时告警。
**自定义查询**：支持自定义查询和分析审计日志。

**审计策略说明**

审计策略定义了审计功能的配置和请求的采集规则。不同审计级别（Audit Level）的事件日志采集规则不同：

| Audit Level | 日志采集规则 |
|---|---|
| None | 符合规则的事件不予采集。 |
| Metadata | 采集请求的Metadata，例如用户信息、时间戳等，但不采集请求体或返回体。 |

容器服务Kubernetes版

| Request | 采集请求的Metadata和请求体，但不采集返回体。不适用于非资源请求（Non-Resource Request）。 |
|---|---|
| RequestResponse | 采集请求的Metadata、请求体和返回体。不适用于非资源请求（Non-Resource Request）。 |

**审计后端说明**

审计事件采集后，会被存储到日志后端文件系统，日志文件为标准的JSON格式。在专有云环境中，审计日志存储于日志服务中对应的日志库。

**前提条件**

集群已处于正常运行状态。 账号下日志服务资源没有超出配额。

### 可观测性

#### 日志管理

介绍如何在ACS集群中配置和使用日志采集，实现应用与控制面日志的统一管理。

**背景信息**

容器计算服务 ACS 默认集成日志服务 SLS（Simple Log Service），为集群提供全面的日志采集与管理能力。可在创建ACS集群时启用日志服务，快速采集集群内的容器日志，包括容器的标准输出以及容器内的文本文件。 在应用层面，SLS 支持通过 Pod 环境变量、AliyunLogConfig CRD 以及 Sidecar 容器等多种方式采集应用日志，满足不同业务场景下的日志收集需求。对于 GPU 类工作负载，可通过 Sidecar 容器方式获取 GPU Pod 的标准输出日志，确保异构计算场景下的日志可观测性。 在控制面层面，ACS 集群的核心控制组件（如 Kube API Server、Kube Controller Manager 等）的日志可由平台自动收集，帮助运维人员快速定位集群运行状态与异常事件。开通 SLS 后，用户可在 SLS 控制台进行日志的查询、分析与可视化，实现 ACS 集群日志的集中管控。

**前提条件**

已开通日志服务 SLS，并完成日志 Project 的创建。 当前账号具备日志服务的管理权限。 账号下日志服务 SLS 的日志库（Logstore）配额充足。

**步骤三：配置日志采集规则**

ACS 支持以下三种日志采集方式，可根据业务需求选择合适的方式。

**方式一：通过 Pod 环境变量配置日志采集**

在 Pod 的 YAML 定义中添加 SLS 相关的环境变量，声明需要采集的日志路径与目标 Logstore。所有与配置相关的环境变量都采用 `aliyun_logs_` 作为前缀。

**创建采集配置的规则：**

```
env:
  - name: aliyun_logs_{Logstore名称}
    value: /var/log/app.log
  - name: aliyun_logs_{Logstore名称}_project
    value: {SLS Project名称}
```

示例中创建了一个采集配置，格式为 `aliyun_logs_{key}` 。 `aliyun_logs_{key}` 表示创建一个名为 `{key}` 的 Logstore（若不存在则自动创建），日志采集路径为 `value` 指定的容器内日志路径。当 `value` 为 `stdout` 时，表示采集容器的标准输出和标准错误输出。

**方式三：通过 Sidecar 容器获取 GPU Pod 标准输出**

针对 GPU 工作负载，在 Pod 中注入 Sidecar 容器，将主容器的标准输出重定向并采集至 SLS，适用于异构计算场景下的日志收集。

**重要**

此方式适用于 ACS GPU/GPU-HPN 计算类型的 Pod。

**原理说明：**

由于 ACS 集群采用 Serverless 形式管理集群资源，不支持部署 DaemonSet，因此日志采集 Agent 需要使用 Sidecar 的形态进行日志采集。Sidecar 模式日志采集 Agent 必须和业务容器共享日志目录，业务容器将日志写入到共享目录中，日志 Agent 通过监控共享目录中日志文件的变化并采集日志。 采集的日志可以分为以下两种：
**标准输出**：采集标准输出依赖于 Medium 为 Stdout 的 EmptyDir 卷。创建 Pod 时可以将该卷挂载到
Sidecar 容器上，Sidecar 可以直接以文件的方式访问 ACS 基础组件收集的标准输出日志。

**说明**

每个 Pod 最多可以声明1个 Medium 为 Stdout 的 EmptyDir 卷，并需要挂载到至少1个容器内。 容器服务Kubernetes版
**文本文件**：采集文本文件可以通过 Pod 内共享的 volume 实现。Pod 内同一个 volume 可以挂载到多

#### Prometheus监控

**背景信息**

容器计算服务 ACS 默认集成 Prometheus 监控能力，为集群提供从基础设施到应用层的多维度监控体系。 通过 Prometheus 监控，用户可以实时掌握集群运行状态、Pod 资源使用情况、容器运行指标以及 GPU 利用率等关键数据，建立对 ACS 集群的全面可观测能力。 ACS 集群支持两种 Prometheus 部署方式：一是安装阿里云 ARMS Prometheus（acs-armsprometheus），与阿里云监控平台深度集成，提供开箱即用的监控大盘与告警能力；二是部署开源 Prometheus，适用于需要高度自定义或已有 Prometheus 生态的场景。无论采用哪种方式，均可覆盖 CPU 使用率、内存使用率、Pod 状态、GPU 利用率等核心指标，满足日常运维与性能调优的需求。
